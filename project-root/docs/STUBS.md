## P1 — влияет на пользователей сейчас

### 1. Восстановление пароля не завершено — ✅ ИСПРАВЛЕНО 2026-10-01
- **Где:** `backend/app/modules/auth/router.py` (`forgot-password`), `backend/app/core/email.py`
- **Было:** токен сброса генерировался и сохранялся, но письмо не отправлялось (нет SMTP).
- **Сделано:** реальная отправка через SendGrid (при заданном ключе) или SMTP (новые настройки `SMTP_HOST/PORT/USER/PASSWORD/USE_TLS`, `FRONTEND_URL` в config.py и .env.example); красивое письмо со ссылкой `{FRONTEND_URL}/reset-password?token=...`. Если почта не настроена — ссылка возвращается в ответе (`reset_link`) и показывается на фронте с кнопками «Копировать»/«Открыть». Попутно исправлен баг: токен не влезал в `users.reset_token varchar(255)` — миграция `f9a0b1c2d3e4` расширяет поле до 512.

### 2. Аналитика: пустые серии спарклайнов — ✅ ИСПРАВЛЕНО 2026-10-01
- **Где:** `backend/app/modules/analytics/router.py` (`/analytics/sparklines`)
- **Было:** три серии из четырёх — `schedule_dev`, `fpy`, `shipments` — всегда `[0]×30`.
- **Сделано:** `schedule_dev` — среднее отклонение факта от плана (actual_end − planned_end, дни) по документам, завершённым в день; `fpy` — доля завершённых документов без привязанных замечаний (carry-forward, по умолчанию 100%); `shipments` → переименован в «Выпуск документов», шт/день по `actual_ready` (таблиц отгрузок в системе пока нет — честный прокси, unit изменён на «шт/день»).

### 3. Аналитика: FPY и отгрузки в KPI-плитках — ✅ ИСПРАВЛЕНО 2026-10-01
- **Где:** `backend/app/modules/analytics/router.py` (`/analytics/kpi`, плитки `fpy_otk`, `shipments_week`)
- **Было:** FPY всегда 0.0%, отгрузки 0/0 с фиктивным подтекстом.
- **Сделано:** FPY — доля утверждённых документов без замечаний (подтекст «Без замечаний: X | С замечаниями: Y», при отсутствии данных — «н/д»); плитка отгрузок → «Выпуск документов (неделя)»: факт (actual_ready за текущую неделю) / план (planned_ready за неделю).

### 4. Календарь: дни рождения всегда пустые — ✅ ИСПРАВЛЕНО 2026-10-01
- **Где:** `backend/app/modules/calendar/router.py` (`/calendar/birthdays`), модель `auth/models.py`
- **Было:** у модели `User` не было поля даты рождения — эндпоинт всегда возвращал `[]`.
- **Сделано:** поле `birthdate` (Date) у User + миграция `f1a2b3c4d5e6`; поле в `UserResponse`/`UserMeUpdate`/`UserUpdate`; эндпоинт возвращает активных пользователей с датой рождения (MM-DD, роль); в настройках профиля (фронт) добавлено поле «Дата рождения», сохраняется на сервер (в демо — в localStorage). Календарь и виджеты дней рождения на фронте уже ждали эти данные — заработали без правок.

### 5. Производственный контроль: карта процесса с пустыми KPI — ✅ ИСПРАВЛЕНО 2026-10-01
- **Где:** `backend/app/modules/production/analytics.py` (`enrich_strategy`), `seed.py`
- **Было:** схема процесса хранилась в БД (seed), но значения KPI по операциям были пустыми.
- **Сделано:** KPI считаются на лету при GET /production/strategy (в БД не сохраняются): загрузка сотрудников — из учёта времени (сопоставление по user_id/ФИО); «Выигранные тендеры», «Кол-во тендеров/мес», «Время подготовки КП» — из тендеров; «% брака при поставке», «% изделий с замечаниями», «Ошибки в ревизии», «Число замен позиций», «Ошибки разводки», «Переделки», «Рекламации» — из замечаний по process_task_id; «Отклонение от плана», «Срок поставки», «Время наладки», «Время выдачи», «Своевременность отгрузки» — из операций по process_task_id. Нормативные значения из seed сохранены; пустыми остаются только метрики без честного источника (Дефицит позиций, Соотв. бюджету и т.п.) и те, у которых ещё нет привязанных данных.
- **Осталось:** привязывать замечания/операции/документы к этапам процесса (в UI есть выбор этапа) — тогда метрики заполнятся автоматически.

## P2 — заметно в отдельных сценариях

### 6. Тендеры: «Статус закупки» — мок
- **Где:** `backend/app/modules/tenders/router_extended.py:485` (`_estimate_materials`)
- **Что:** материалы и сроки поставки по тендеру вычисляются эвристикой по типу проекта — не реальные данные.

### 7. Отчёты: генерация возвращает фиктивный URL
- **Где:** `backend/app/tasks/reports.py:8` (Celery)
- **Что:** задача возвращает `url: /reports/123.pdf`, файла нет.
- **Чинить:** реализовать генерацию (reportlab/weasyprint) и складывать в storage; до этого — возвращать честную ошибку, а не фиктивный URL.

### 8. Экспорт данных (Celery) не реализован
- **Где:** `backend/app/tasks/reports.py:22`
- **Что:** задача-заглушка, ничего не экспортирует.
- **Чинить:** реализовать выгрузку моделей в csv/xlsx (pandas/openpyxl уже есть в окружении).

### 9. Уведомления: email/push не отправляются — ✅ ИСПРАВЛЕНО 2026-10-01
- **Где:** `backend/app/tasks/notifications.py`; `backend/app/core/telegram.py`
- **Было:** Celery-задачи возвращали фиктивный `status: completed`, ничего не отправляя; Telegram-модуль требовал неустановленный пакет `telegram` и имитировал отправку печатью в консоль.
- **Сделано:** Celery-задачи отправляют по-настоящему: `send_email` — через настроенный SMTP/SendGrid (п. 1); `notify_project_members` — ищет руководителя и создателя проекта и шлёт им письмо (с учётом `email_notifications_enabled`); если транспорт не настроен — честный `status: "skipped"` с причиной. `core/telegram.py` переписан на httpx (Bot API): при заданном `TELEGRAM_BOT_TOKEN` сообщения уходят реально, иначе — запись в лог. `send_push` остаётся skipped — push-транспорт (FCM/WebPush) в системе нет.
- **Примечание:** внутриприложенные (веб) уведомления работали и раньше; письма маршрутов согласования отправляются через `core/email.py` с момента исправления п. 1. Celery в локальном venv не установлен — задачи выполняются в окружениях, развёрнутых по requirements.txt.

### 10. Документы: Celery-задачи PDF и обработки файлов
